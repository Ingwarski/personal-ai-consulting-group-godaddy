# Порядок JSON-ключів у відбитку агентського повідомлення

## Фактичний стан

2026-09-07 після входу користувача через Chrome отримано й опубліковано `79f9b2916de931bf4aefdb64f8a08556b34e8eea`. У вкладці Published підтверджено саме цю ревізію та обидва OK. Один наступний тест попросив незалежного Критика перевірити вже надану рекомендацію для вигаданої кав'ярні. Початкову задачу та згоду не дублювали. Бот прийняв запит, але потім захищений status показав:

```json
{"setupMode":"disabled","configured":true,"ready":false,"reason":"outbox_blocked","consultationWorking":false,"consultationBlocked":true,"consultationFailure":{"stage":"readiness","code":"unknown"}}
```

Нових агентських реплік у Element не було. Вміст рядків БД, секрети та сирі винятки не витягували.

## Відтворений дефект

`confirmedMessageFingerprint` канонізував зовнішні поля, але хешував вкладене `authority` у довільному порядку ключів. Перестановка лише `agentId/provider/runtimeSessionRef/kind` за незмінних значень дала різні SHA-256. Це відтворено локально; тест читання outbox після перестановки також впав. MySQL офіційно попереджає, що JSON-ключі сортуються, а порядок не гарантований між версіями: [The JSON Data Type — Normalization](https://dev.mysql.com/doc/refman/8.0/en/json.html#json-normalization), перевірено 2026-09-07.

Це узгоджується з тим, що контрольні/прямі повідомлення без authority доставлялися, а перші агентські — ні. Live status сам по собі не показує конкретної причини невідповідності відбитка; остаточна перевірка цієї причинної гіпотези — відновлення тих самих записів після code-only ремонту.
