# Same-app Matrix wake setup

This opt-in gateway supplements continuous authenticated Matrix sync and automatic recovery. It does not replace encrypted sync or the durable ingress/outbox. No Settings visit, local background process or additional service is required after setup. Opening `/healthz` is not a readiness check.

1. Deploy the wake/recovery code to the existing Published GoDaddy app. Do not enable it in Preview. Preserve its current Matrix device, crypto store, passphrase and database.
2. Generate a dedicated secret once with `node -e 'process.stdout.write(require("node:crypto").randomBytes(32).toString("hex"))'`. Store it in the Published secrets as `MATRIX_WAKE_PUSH_KEY`. Do not reuse a Matrix access token or session key. Add `MATRIX_WAKE_ENABLED=TRUE`. Do not log or paste either credential into chat.
3. Preserve the existing `RUNTIME_MODE=production`, `GODADDY_STATE_DATABASE_ROLE=published`, `MATRIX_HOMESERVER_URL=https://matrix.org`, `MATRIX_ROOM_ID`, `MATRIX_OWNER_MXID`, `MATRIX_BOT_MXID`, `MATRIX_BOT_DEVICE_ID`, `MATRIX_ACCESS_TOKEN`, and exact `SETTINGS_PUBLIC_ORIGIN`. `MATRIX_SETUP_MODE` must be absent or `disabled`. The dedicated app ID is `ai.personal-consultant.matrix`.
4. In an explicitly authorized operator environment with those secrets already available, run `node --experimental-strip-types scripts/register-matrix-wake.ts` to validate configuration without any network call. Then run the same command with `--apply` to verify the bot/device and gateway, inspect current account configuration and add only the dedicated pusher and owner-room override. This one-time CLI does not become a local runtime. It uses `append: true` and never deletes another pusher or replaces other rules. A conflicting dedicated rule/pusher is an error, not permission to overwrite it.
5. If registration partly fails, inspect the dedicated pusher/rule and retry: matching existing entries are retained. Do not remove the bot device or reset its crypto store. Rules earlier in the existing override order (including a user's master mute) can suppress notifications; inspect them without silently changing them. The new rule matches only the configured room and owner sender, including encrypted room events. Verify actual homeserver delivery, not just successful registration.
6. Close all Settings tabs. Send a new owner message in the verified Matrix room. Confirm one durable intake and exactly one consultation. Repeat after an idle period and an authorized Published process restart/redeploy; verify unchanged store fingerprint, bot identity and cursor continuity. Test duplicate hints, temporary network/storage failure and recovery. Registration success alone is not this live proof.

The endpoint is `https://<existing-Published-host>/_matrix/push/v1/notify`. It accepts bounded `event_id_only` hints containing the dedicated app ID/pushkey and configured room. It never treats notification content as a user message or calls a model. Invalid hints do not wake anything; valid but unavailable transport returns a retryable error and never rejects/deletes the valid pushkey. Missing, corrupt, inaccessible or mismatched identity remains blocked: the code never recreates it. Restore the original trusted state through a separately authorized repair if required.

Primary references: [Matrix Push Gateway API](https://spec.matrix.org/latest/push-gateway-api/) and [HTTP pusher registration](https://spec.matrix.org/v1.19/client-server-api/#post_matrixclientv3pushersset).
